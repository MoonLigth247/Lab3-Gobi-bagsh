## SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл | Үндэслэл |
|---|---|---|---|---|
| Performance | /cart/add latency | p95 < 200 мс | 20 VU, 1 мин | Localhost дээр 1-5мс хариулдаг тул 200мс нь бодитой дээд хязгаар |
| Reliability | /pay error rate | < 8% | 20 VU, 1 мин | Серверт 5% алдаа суулгасан тул 8% нь бодитой босго |
| Availability | Бүх хүсэлтийн амжилтын хувь | ≥ 90% | 20 VU, 2 мин, 10с зогсолт | 10с зогсолт 120с цонхны ~8.3% тул 90% бодитой |
| Report (нэмэлт) | /report latency | p95 < 450 мс | 20 VU, 1 мин | Сервер 200-400мс санамсаргүй хүлээлттэй тул 450мс дээд хязгаар |

### Error budget тооцоо (цагаар)
2 минутын цонхонд 90% availability = 10% эвдрэх эрх = **12 секунд**.

### Chaos дүгнэлт

- **Бодит availability:** 77.97% (амжилттай: 2275, нийт: 2919)
- **http_req_failed{name:pay}:** 24.56%
- **Цагаар тооцсон 12с budget:** 10с зогсолт нь 2 минутын цонхны 8.3% тул 90% SLO-д багтах ёстой байсан.
- **ХҮСЭЛТЭЭР тооцоход:** 22.02% алдаа гарсан. Учир нь WSL2-д сервер унасан үед хүсэлт агшин зуур (connection refused) буцдаг бөгөөд /report-ын 200-400мс хүлээлт алга болдог тул зогсолтын 1 секунд хэвийн секундээс олон хүсэлт "иддэг".
- **Availability threshold:** FAIL (77.97% < 90%)
- **Reliability threshold:** FAIL (24.56% > 8%)
- **Дүгнэлт:** Нэг эвдрэл (сервер зогсолт) хоёр SLO-г зэрэг зөрчсөн. Availability ба reliability SLI-г тусгаарлахын тулд reliability-г зөвхөн сервер ажиллаж байх үеийн /pay хүсэлтээр тооцох, эсвэл availability-г тусдаа endpoint-оор хэмжих хэрэгтэй.

### Fail туршилт

- /report threshold p(95)<100 → FAIL (сервер 200мс-ээс хурдан хэзээ ч хариулдаггүй)
- Exit code: 99
- CI pipeline яг энэ exit code-оор build-ийг зогсоодог.
- /cart/add-ыг p(95)<50 болгоход PASS хэвээр үлдэнэ — localhost дээр 1-5мс хариулдаг тул.

## Дүгнэлт

Энэ лабораторид чанарын сценариог 6 хэсэгтэй форматаар бичиж, SLO болгон томьёолж, k6 threshold болгон кодчилсон. Хамгийн хэцүү нь босгыг бодитой тоо сонгох байсан — localhost дээр /cart/add 1-5мс хариулдаг тул p95<200 нь хэт сул босго болж, харин /report 200-400мс тул p95<100 нь зориуд FAIL болгосон. Chaos туршилт нь availability сценариогийн хэмжүүрийг батлав — 10с зогсолт нь 2 минутын цонхонд 8.3% эвдрэл үүсгэж, 90% SLO-г хүсэлтээр тооцоход FAIL болгосон. Гэхдээ цагаар тооцсон 12с budget-д багтах ёстой байсан нь хоёр тооцооны зөрүүг харуулсан. Availability ба reliability SLI-г тусгаарлах нь чухал — сервер унасан үед /pay-ийн хүсэлт бүр унадаг тул нэг эвдрэл хоёр SLO-г зэрэг зөрчдөг. k6-ийн checks нь ХҮСЭЛТИЙН хувь, цагийн биш гэдгийг ойлгосон. Exit code (99) нь CI pipeline-д build зогсооход ашиглагддаг. Ирээдүйд бодит сервер дээр илүү нарийн босго сонгох шаардлагатай.

### 1. Орчны бэлтгэл (WSL2 + Ubuntu 24.04)

Энэ лабораторийг Windows 11 дээр WSL2 ашиглан хийсэн. WSL2 суулгах явцад хэд хэдэн алдаа гарсан:

- **WSL суулгах алдаа:** `REGDB_E_CLASSNOTREG` — Windows-ийн бүртгэлийн алдаа. Шийдэл: Microsoft-ын GitHub-аас `wsl.2.x.x.x64.msi` гараар татаж суулгасан.
- **Ubuntu татах алдаа:** `0x80072f7d` (secure channel support) — TLS 1.2/1.3 тохиргооны алдаа. Шийдэл: Registry-ээр TLS 1.2/1.3 идэвхжүүлж, компьютер restart хийсэн.
- **Ubuntu суулгах:** `wsl --install -d Ubuntu-24.04` амжилттай болсон. Хэрэглэгчийн нэр: `munhu`.

**Ажлын орчин:**
- Windows 11
- WSL2 + Ubuntu 24.04 LTS
- Node.js v20.20.2 (NVM-ээр суулгасан)
- npm v10.8.2
- k6 v2.3.0

### 2. Node.js суулгах явцад гарсан алдаа

`sudo apt install -y nodejs` дээр `Hash Sum mismatch` алдаа гарсан. WSL2-ийн сүлжээний давхаргаас үүдэлтэй. Шийдэл:

1. APT кэшийг цэвэрлэх: `sudo rm -rf /var/lib/apt/lists/* && sudo apt clean`
2. NodeSource-ийн GPG key нэмэх
3. NodeSource repo нэмэх
4. Гэхдээ `Error reading from server - read (5: Input/output error)` гарсан тул **NVM** ашигласан:
   ```bash
   curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
   source ~/.bashrc
   nvm install 20
   nvm use 20
   nvm alias default 20
